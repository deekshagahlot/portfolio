TESTING FOUR WAYS TO HAND OVER A DESIGN SYSTEM

Which format of design system context actually works

OVERVIEW

I gave the same build brief to Claude four times, changing only how the design system was supplied — screenshots, a PDF export, a live Figma MCP connection, and a hand-written token document. I wanted to know which format produced output closest to the design, and whether the live connection was worth the setup.

THE PROBLEM

Every AI design conversation starts by re-explaining the system

Working with an agent means describing your system again at the start of every session — colours, spacing scale, type ramp, what a primary button looks like in each state. Most people solve this by pasting a screenshot and hoping. The output looks approximately right and is wrong in the details, and the details are the whole job.

The underlying question isn’t “which model is best.” It’s what a model can actually read.

APPROACH

One brief, four kinds of context

I built the same component four times, holding the prompt constant and changing only what the model had to work from.

Screenshots. A frame image plus a written description. The model has to infer values from pixels.

PDF export. A styles page exported from Figma. Looks like documentation, but the model reads it as flattened images and text with no reliable relationship between a swatch and its name.

Figma MCP. A live connection to the file. The model reads frame structure, spacing, and component hierarchy directly instead of guessing from an image.

Token markdown. A hand-written design-system.md: semantic names, hex values, spacing scale, type ramp, component rules, and what each token is for.

I scored the output on correct hex values, spacing within 4px, states present, and naming matched to the codebase.

LEARNING
What the ranking actually was

Token markdown and MCP both beat the image formats, but for different reasons — and they aren’t substitutes. MCP is precise about this frame: real spacing, real hierarchy, real nesting. The token doc is precise about the system: what a value means, when to use it, what it’s called. MCP told the model what was there. The doc told it why. Screenshots and PDF sat far below both, and PDF was the worst of the four — it wears the costume of documentation while carrying almost none of the structure.

HICCUP
Where it still needed me

MCP returned accurate values for things I hadn’t decided yet, and the model treated a placeholder as a rule. The token doc was correct but incomplete — no focus states documented, so it invented them plausibly and wrongly.

OUTCOME

The doc mattered more than the connection

The best setup was both — the token document as standing context, MCP for the frame in front of me. But if I had to drop one, I’d keep the doc. A model with good vocabulary and no live connection still produces work I can review. A model with a live connection and no vocabulary produces work that matches the frame and misses the system.

What I use now: design-system.md in the project, read on every task. MCP when I’m building a specific frame. Screenshots only for intent — never for values.
