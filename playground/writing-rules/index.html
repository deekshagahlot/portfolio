WRITING THE RULES DOWN ONCE INSTEAD OF EVERY SESSION

Turning content guidelines into a reusable skill

OVERVIEW

I stopped re-explaining my copy standards in every prompt and wrote them down once as standing context — tone, casing, CTA patterns, error structure. Then I ran the same set of copy briefs with and without the rules loaded, to see whether encoding beat explaining.

THE PROBLEM

Tone is the first thing to drift

Visual inconsistency gets caught. Someone notices two greys, or spacing that doesn’t sit on the scale. Copy inconsistency slips through, because every individual string reads fine on its own — it’s only across twenty screens that you notice the CTAs sometimes take a verb and sometimes don’t, or that half the error messages say what broke and the other half say what to do about it.

Working with a model makes this worse, not better. It writes fluently in a default voice that isn’t yours, and correcting it string by string is slower than writing the string yourself.

APPROACH

Write the rules, then test them against no rules

I wrote my content standards as a single document — not a style guide for humans, but instructions specific enough that a model could apply them without judgement calls: sentence case everywhere, including buttons and headings; CTAs verb-first, naming the outcome rather than the mechanism; errors saying what happened and what to do next, in that order, never why; never “please”, never “oops”, never exclamation marks; second person for the user, never “we” for the product.

Then I ran the same copy briefs twice — once with the document loaded, once without — and compared how much I had to edit.

LEARNING
Writing the rules taught me more than using them

The useful part wasn’t the output. It was discovering that several things I’d have described as my standards weren’t rules at all — they were case-by-case judgement I’d been calling consistency. Anything I couldn’t write as an instruction was, by definition, something I’d been deciding fresh each time — and that’s a gap in the system, not a gap in the model.

HICCUP
Rules cover the ordinary cases

With the rules loaded, output was consistent and unremarkable — correct, and slightly flat. The document is good at preventing wrong copy and no help at all in producing the line that actually lands. Knowing when to break a rule you wrote yourself is still the part that needs a person.

OUTCOME

A style guide that finally gets used

The document does two jobs now. It’s standing context in every session, so I stop paying the re-explanation tax. And it’s a written standard that survived being made explicit — which the informal version in my head never had to do.

The honest measure of success isn’t the time saved. It’s that I now have content rules I could hand to another designer, which I didn’t before this, and wouldn’t have written without a reason to.
